# アーキテクチャ検討・設計判断（02_system-requirements.md ベース）

## 目的
- docs/requirements/02_system-requirements.md（要件定義書）を前提に、
    システム全体のアーキテクチャ候補を洗い出し・比較・評価する。
- 非機能要件（パフォーマンス / 可用性 / 保守性 / セキュリティ 等）に対する
    各アーキテクチャの適合度を明示する。
- 最終的に採用するアーキテクチャの「判断材料」を構造化し、
    ADR 作成コマンド（adr-create.md）の入力とする。

このコマンドは **「考えるフェーズ（検討・比較・評価）」を担い、
ADR はその結果の「正式記録」として後続フェーズで作成する** こと。

---

## 入力

必ず以下のファイルを前提とすること：

- docs/requirements/02_system-requirements.md
- 必要に応じて：
    - docs/requirements/01_stakeholder-needs.md
    - 既存 ADR（既存システム拡張の場合）

追加で、ユーザーから以下のような補足を受け取ってもよい：

- 想定している技術スタックの制約（例：Python/Qt/C#.NET の縛り）
- インフラ（オンプレ / クラウド / コンテナ）の制約
- 将来の拡張方針（マイクロサービス化を見据えるか、など）

入力例：

<<<02_system-requirements の要約 or ファイルパス>>>
<<<補足情報（任意）>>>

---

## 出力

docs/design/01_architecture-evaluation.md を生成する。
構造は以下の **固定テンプレート** に従うこと。

**見出し構造は絶対に変更してはならない。**

# 01. Architecture Evaluation

## 1. Context（文脈）
- システムの概要（02_system-requirements.md の Overview から要約）
- 想定される利用シナリオ
- 技術・組織・運用上の制約の整理
    （Constraints / Non-Functional Requirements から抽出）

---

## 2. Quality Attributes（品質特性）
docs/requirements/02_system-requirements.md の非機能要件から、
アーキテクチャ設計で特に重視すべき品質特性を列挙する。

| ID        | Attribute      | 説明                                 | 関連 REQ-NF |
|-----------|----------------|--------------------------------------|------------|
| QA-001    | Performance    | 応答時間・スループットなど           | REQ-NF-xxx |
| QA-002    | Availability   | 稼働率・冗長化要件                   | REQ-NF-yyy |
| ...       | ...            | ...                                  | ...        |

---

## 3. Candidate Architectures（候補アーキテクチャ）
検討対象とするアーキテクチャ候補を 2〜4 個程度に絞り、
それぞれの概要と構成要素を記述する。

### 3.1 Candidate A: <アーキテクチャ名>
- 概要
- 主な構成要素（例：API サーバ、フロントエンド、DB、メッセージキュー 等）
- 採用する主な技術スタック（言語 / FW / DB / インフラ）

### 3.2 Candidate B: <アーキテクチャ名>
- 概要
- 構成要素
- 技術スタック

（必要であれば 3.3, 3.4 を追加）

---

## 4. Evaluation（評価）

### 4.1 Quality Attributes × Candidate マトリクス

各候補ごとに、2章で列挙した品質特性に対する適合度を評価する。

| QA \ Candidate | A（<名前>） | B（<名前>） | コメント（重要な理由） |
|----------------|------------|------------|------------------------|
| QA-001         | ◎ / ○ / △ / × | ◎ / ○ / △ / × | 主要な理由を 1〜2 行で |
| QA-002         | ◎ / ○ / △ / × | ◎ / ○ / △ / × |                        |
| ...            | ...        | ...        | ...                    |

### 4.2 リスクとトレードオフ

各候補ごとに、主要なリスクとトレードオフを整理する。

#### Candidate A
- 強み
    - ...
- 弱み / リスク
    - ...
- 向いているケース / 向いていないケース

#### Candidate B
- 強み
- 弱み / リスク
- 向いているケース / 向いていないケース

---

## 5. Recommended Architecture（推奨アーキテクチャ）

### 5.1 採用するアーキテクチャ
- 採用候補：Candidate <X>（<名前>）
- 採用理由：
    - 主要品質特性（QA-xxx）に対する適合性が最も高い
    - 既存システム / チームスキルとの整合性
    - 将来の拡張性

### 5.2 選択しなかった候補と理由
- Candidate Y を採用しない理由
- 長所はあるが、今回は優先度が低い・制約に合わないなど

---

## 6. Impact & Risks（影響とリスク）

- 開発コストへの影響
- 運用コストへの影響
- 組織・プロセスへの影響
- 技術的負債になりうるポイント
- リスク軽減策の概要

---

## 7. Inputs for ADR（ADR 作成のための要約）

ADR コマンド（adr-create.md）に渡すための要約情報。

- **Problem（問題）**
    - どのような要求・制約のもとでアーキテクチャを決める必要があるか
- **Decision（決定）**
    - 採用するアーキテクチャと、その一文要約
- **Alternatives（代替案）**
    - 検討した候補と、採用しなかった理由を箇条書きで
- **Rationale（根拠）**
    - なぜこのアーキテクチャが最も合理的と判断されたか
- **Consequences（結果・影響）**
    - ポジティブ / ネガティブ両面の影響をまとめる

adr-create.md では、この 7 章の内容をそのまま ADR の各セクションに流用してよい。

## 禁止事項

- docs/requirements/02_system-requirements.md の内容や構造を勝手に変更しないこと。
- STK / REQ-F / REQ-NF の ID を再定義・再採番しないこと。
- 「アーキテクチャ検討」と「最終決定（ADR）」を混同しないこと。
    本ドキュメントは **検討結果の記録** にとどめ、
    最終決定は ADR で行う前提とする。
