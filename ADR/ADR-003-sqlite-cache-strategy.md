# ADR-003: SQLite キャッシュ方式によるデータストア戦略

## Status
Accepted

## Context
- データストアとして SQLite を使用することが技術制約で決定されている
- 関連要件: REQ-F-001（プロジェクト契約インポート）、REQ-F-002（工数実績インポート）、REQ-F-003（休日マスタインポート）、REQ-F-008（データ再読み込み）
- データソースは外部の CSV / JSON ファイルであり、日次で手動取り込みされる
- データ更新頻度は日次であり、リアルタイム性は不要である
- Single Source of Truth の方針を明確にする必要がある

## Decision
- 外部 CSV / JSON ファイルを Single Source of Truth（マスタデータ）とする
- SQLite は「表示・集計のためのキャッシュ」として機能させる
- データフロー: 外部ファイル → アプリ（インポート処理・バリデーション）→ SQLite → アプリ（集計・グラフ生成）→ UI
- 日次で CSV / JSON を再取り込みし、SQLite を上書き更新する
- データの整合性は CSV データで上書きすることで保証する
- バックアップ機能として SQLite の内容を CSV / JSON 形式でエクスポート可能にする（REQ-NF-006）

## Alternatives
- **SQLite をマスタデータベースとする方式**: SQLite に直接データを入力・編集し、CSV / JSON は単なるインポート元とする。データの整合性管理が複雑になり、CSV 編集後の再取り込み時に差分検出・マージ処理が必要になる。
- **CSV / JSON のみでデータストアなし**: 毎回 CSV / JSON を読み込んで集計処理を行う。パフォーマンスが低下し（特に工数実績 5000 件の集計）、要件の性能基準（チャート描画 3〜5 秒）を満たせない可能性が高い。
- **外部データベース（PostgreSQL / MySQL）**: ローカル実行のデスクトップアプリであり、DB サーバーの構築・運用コストが不要な SQLite の利点を失う。マルチユーザー同時接続が不要な本プロジェクトには過剰である。

## Rationale
- 外部 CSV / JSON ファイルを Single Source of Truth とすることで、データ管理の責務を明確化できる
- ユーザーは別ツール（Excel 等）で CSV を編集し、再取り込みするだけで済むため、操作性が向上する
- SQLite をキャッシュとして扱うことで、CSV / JSON の変更を常に正とし、整合性の問題を回避できる
- パフォーマンス要件（CSV 読み込み: 5〜10 秒、チャート描画: 3〜5 秒）を満たすために、SQLite による集計・インデックス機能を活用できる
- SQLite のエクスポート機能により、バックアップとリストアが容易である

## Consequences
### Positive
- データの整合性管理がシンプルになる（CSV / JSON を再取り込みすれば SQLite が上書きされる）
- ユーザーは慣れたツール（Excel 等）で CSV を編集でき、学習コストが低い
- SQLite のインデックス・集計機能により、パフォーマンス要件を満たせる
- バックアップとリストアが CSV / JSON 形式で可能であり、可搬性が高い
- SQLite ファイルの破損時でも、CSV / JSON から再取り込みすることで復旧できる

### Negative / Risks
- CSV / JSON と SQLite の整合性が取れなくなるリスクがある（軽減策: 再取り込み時に SQLite を完全上書き更新し、整合性チェック機能を追加）
- CSV / JSON ファイルを誤って削除・上書きした場合、データが失われる（軽減策: ユーザーに定期的なバックアップを推奨、エクスポート機能の提供）
- 大規模データ（プロジェクト数 1000 件以上、工数実績 10 万件以上）では SQLite のパフォーマンスが低下する可能性がある（現在の想定: プロジェクト 50 件、工数実績 5000 件）
